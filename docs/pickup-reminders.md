# Friday pickup reminders

Paid, confirmed orders receive a customer pickup reminder on their pickup Friday. On Vercel Hobby, the schedule normally starts between **9:00am and 9:15am Pacific**. The reminder uses React Email, the existing confirmation layout/PNG wordmark and Resend transport. Initial wording is playful: “You have a hot date. With focaccia.” The email includes the saved order number, items, sizes, quantities, line totals, order total, pickup date/window, published email-only pickup address/directions and secure confirmation link. Launch pickup is **2–6pm**. Saved pickup windows remain authoritative for existing orders. The published address currently comes from **Commerce Copy → Order Email → Pickup Address**, also used by confirmations.

This is an order service message, sent regardless of newsletter opt-in or marketing unsubscribe status. It neither changes marketing preferences nor adds promotional content. One reminder is sent per order; a customer with multiple orders receives each order's details separately. Pending/unreconciled payments, cancelled orders, fulfilled orders and fully refunded orders are excluded. Partially refunded, still-confirmed orders remain eligible; their summary uses the original saved order totals. Special-order inquiries are not commerce orders and are excluded. Published product availability and blackout changes do not erase an existing paid order's reminder.

## Activation

1. Refresh any expired QA credentials in the gitignored `.env.local`. Apply `npm run db:migrate-test` and run `npm run test:integration` against the isolated `TEST_DATABASE_URL` before applying the additive migration with `npm run db:migrate` against the intended app database's direct `DATABASE_URL_UNPOOLED`. The migration only adds `pickup_reminders` and does not backfill historical email sends.
2. Run `npm run cms:migrate-pickup-reminder -- --dry-run`, then `npm run cms:migrate-pickup-reminder`. This initializes only absent **Reminder Subject**, **Reminder Heading** and **Reminder Body** fields in an existing nonempty Order Email group. Existing wording, drafts, cleared groups and cleared fields are preserved. Review the reminder and pickup details in Studio. Runtime delivery reads published Sanity wording; migration/preview fixtures never become frontend or email fallbacks. An uninitialized reminder group fails delivery instead of accidentally using confirmation wording. Cleared individual fields disappear.
3. In the intended Vercel Production environment, configure the existing `DATABASE_URL`, Sanity read configuration/token, `RESEND_API_KEY`, `EMAIL_FROM`, `ORDER_CONFIRMATION_SECRET` and public HTTPS `NEXT_PUBLIC_SITE_URL`. Add a private random **`CRON_SECRET` of at least 32 characters** and set **`PICKUP_REMINDERS_ENABLED=true`**. Keep the reminder flag unset/false in Preview environments. Preview deployments also refuse sends when `VERCEL_ENV=preview`, even if the flag is accidentally enabled. Never deploy a Sanity write token.
4. Deploy only after an explicit deployment request, per `AGENTS.md` and [the deployment runbook](deployment.md). In the Vercel dashboard, confirm that `pickup-reminders` is active under **Schedules** in Production and that the function duration is 300 seconds with **Fluid compute**. Verify authentication with the send flag disabled in the test deployment. Use an authorized test recipient and order in an isolated environment for inbox verification.

`vercel.json` defines one static schedule at **`0 9 * * 5`** in **`America/Los_Angeles`**. Vercel handles daylight saving time and sends an authenticated GET request to `/api/cron/pickup-reminders`. A new static schedule starts active in Production and inactive in Preview. To pause it, disable `pickup-reminders` in the Production **Schedules** view. The worker admits scheduled starts only during the **9:00–9:59am Pacific** hour, including late arrivals within that window. [Vercel schedule timing and environments](https://vercel.com/docs/schedules/concepts)

## Delivery, concurrency and recovery

`pickup_reminders` is a separate durable delivery record with one unique row per order. It stores the immutable rendered HTML/plain text and recipient, a stable `salted-pickup/<delivery-id>` Resend idempotency key, a short worker lease and provider acceptance state. Retries reuse the saved payload even if CMS copy or sender configuration changes. Confirmation outbox rows and `orders.notification_status` are unchanged. Network calls and React rendering run outside database transactions. Workers lock the order and recheck current payment/fulfillment before claiming delivery.

The handler requires the exact `Authorization: Bearer <CRON_SECRET>` header before reading order data. Missing/short secrets fail closed, responses are never cached, and only delivery counts or generic errors are returned. No addresses, capabilities, provider responses or customer details enter application logs. The flag defaults off. Creating the files or running `email:preview` sends nothing.

Each invocation has a **240-second work budget within a 300-second function**, supported by [Hobby with Fluid compute](https://vercel.com/docs/functions/configuring-functions/duration). It scans in pages rather than capping the recipient list, leaving time for its final provider request and bookkeeping. A run admitted during the 9am hour may finish after 10am; it still stops if the date changes or pickup begins at 2pm. Newly invoked scheduled runs at/after 10am remain skipped.

Nonzero failure, remaining or review counts return HTTP 503 for operator visibility. Check the Friday run under **Schedules** in Vercel. If it failed, timed out or left unfinished deliveries, use the private recovery command below before pickup. Allow any active delivery lease to expire before recovery. Sent records and stable Resend keys prevent duplicates. Very large recipient lists or provider outages may require multiple manual runs. Check Resend for delivery and bounces. The `sent` state records provider acceptance. [Vercel retry behavior for HTTP path schedules](https://vercel.com/docs/schedules/concepts#retries)

For private recovery, run `npm run commerce:pickup-reminders` with the intended environment and `PICKUP_REMINDERS_ENABLED=true`. It can send only on the current Friday from 9am until pickup starts at **2pm Pacific**. It cannot target a past date or bypass payment/fulfillment checks. At other times it returns `skipped`. This command handles reminders only; payment recovery and rate-limit cleanup remain private operator actions and are not scheduled here.

Resend's [idempotency retention](https://resend.com/docs/dashboard/emails/idempotency-keys) is 24 hours. Attempts older than 23 hours move to `review`. Investigate the stable key in Resend before changing a delivery's state; never blindly reset an ambiguous attempt. The payload contains order capabilities and customer information and inherits the order data's access and retention requirements. A refund/cancellation that commits after a worker has claimed a message cannot retract a provider request already in flight.
