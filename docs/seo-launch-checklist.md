# Search launch checklist

## Before approving activation

- Review the [SEO audit](seo-audit.md), [route inventory and architecture](seo-implementation.md), [content review](seo-content-recommendations.md) and [local listing eligibility](local-seo-checklist.md).
- Review final pickup facts, product and recipe availability, photos, placeholder copy, legal wording and the business’s public contact details. Use the published page-level hide control for pages that should wait, including the empty recipes landing page if recipes are still pending.
- Attach the production domain to the intended Vercel project only after authorization, following the [deployment runbook](deployment.md). The domain currently serves a Squarespace placeholder. Confirm DNS, HTTPS, the Vercel hostname mapping, and the permanent www-to-apex redirect, including a deep path. Keep staging as a separate QA hostname.
- Keep `SEO_INDEXING_ENABLED=false` or unset for the initial deployment and all preview environments. Ensure Vercel security allows legitimate public requests to storefront pages and images once launched. Check WAF and bot-policy settings using published crawler identities and operator logs. Retain existing security and authorization on private endpoints.
- Review the existing checkout launch status separately. The repository still has a Stripe test-key guard. Confirm that the intended production order path is authorized and ready before promoting online ordering. This SEO flag has no effect on checkout.
- Optionally verify a Google Search Console **Domain** property with its DNS TXT record and verify Bing through the supported ownership flow. Publish only real tokens. If a website tag is needed instead, set `GOOGLE_SITE_VERIFICATION` and/or `BING_SITE_VERIFICATION`; the published apex homepage emits the appropriate tag. [Google ownership verification](https://support.google.com/webmasters/answer/9008080) · [Bing Webmaster Tools](https://www.bing.com/webmasters/about)

## Approved activation

1. With explicit approval, set the server environment variable `SEO_INDEXING_ENABLED=true` on the intended Vercel production deployment and redeploy. Both the build and runtime must see the value. Clear the global Sanity hide switch if set.
2. Use **GET** plus a browser on the homepage, Pickup, an active product, a size query URL, Recipes and an eligible published recipe. Check HTTP 200, production canonical and metadata. Confirm no inherited or platform-added `noindex` header or tag on eligible apex URLs. Confirm `/studio`, `/links`, `/order/*`, legal/preference routes, staging and Vercel preview URLs keep noindex. Check 404s for missing slugs.
3. Verify `/robots.txt` advertises the production sitemap and allows public pages and assets. Verify `/sitemap.xml` lists the intended published 200 URLs. Check the X-Robots-Tag on staging and confirm that stage remains available for QA. Recheck one crawled image and the default social card after DNS cutover.
4. Submit the sitemap in Google Search Console. Inspect the homepage and representative product and recipe URLs, check the live HTML, and then request indexing where useful. Confirm Google's selected canonical and revisit Page indexing after crawling. [Google sitemap submission](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap) · [URL Inspection](https://support.google.com/webmasters/answer/9012289)
5. Add the domain to Bing Webmaster Tools, verify it or import the verified Search Console site, submit the same production sitemap, and check URL Inspection and crawl reports. IndexNow is deferred until publishing frequency justifies a verified, production-only integration. [Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a) · [IndexNow protocol](https://www.indexnow.org/documentation)
6. Use Google Rich Results Test and the Schema.org validator on real public URLs. Review actual product or recipe warnings after approved assets and content are published. [Rich Results Test](https://search.google.com/test/rich-results) · [Schema.org validator](https://validator.schema.org/)

## Monitoring and rollback

- Review indexed pages, impressions, clicks, query clusters, device and Google Images performance weekly at first. Review Product/Recipe enhancements when reports appear. Track local Maps visibility only after eligibility and verification. Check a small set of genuine customer questions in AI search and compare observable referrals in GA4. Complete AI citation and impression counts are unavailable.
- Compare organic sessions and the existing add-to-bag, pickup and special-order conversions with the baseline. Consider product-view or recipe engagement events if they answer a reporting question. Add purchase measurement only with server-verified payment, an opaque deduplication identity and reviewed consent/privacy controls. The existing GA4 code remains the single analytics integration.
- Review mobile Core Web Vitals in Search Console when field data accrues. Good field thresholds at the 75th percentile are LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1. Run repeatable lab measurements to investigate regressions. [Google Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals)
- If launch approval is revoked, disable the flag and rebuild/redeploy. Confirm the apex returns noindex and the sitemap is no longer advertised. Use the CMS page switch for individual URLs. Review crawler reports after recrawl.
