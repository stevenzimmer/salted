## Initial planner review and implementation

The official Stripe plugin was available. Its implementation planner was invoked before implementation against the connected **salted sandbox** (test mode). Guide `iguide_61Vifcp0Q9GRXBVBX41ETB3yZeGSH` accepted the browser / physical goods / standard checkout / hosted Checkout path (`out_of_box_hosted`). No fallback skill installation was needed.

Business context supplied: Salted Focaccia, saltedfocaccia.com; small-batch homemade sourdough focaccia and bread, multiple sizes/flavors, one-time purchases, local pickup Fridays 14:00–18:00 Pacific, date selected before payment, limited variant/date inventory, Wednesday 23:59:59 Pacific cutoff, Next App Router / React / TypeScript / Tailwind / shadcn, Sanity Visual Editing, Vercel, Neon Postgres and Drizzle.

Use Stripe-hosted Checkout Sessions in payment mode with inline `price_data` derived from fresh published Sanity content. Sanity remains the catalog; no manually maintained Stripe catalog. Persist integer-cent price/name snapshots before calling Stripe. Postgres transactions reserve stock; no database transaction remains open during an external API request. Stripe idempotency keys recover uncertain Session creation. Verified webhook payment status fulfills orders; browser redirects never fulfill them.

The planner recommends Dynamic Payment Methods, Link and Adaptive Pricing for conversion. Deviations: USD is fixed and Adaptive Pricing is disabled so totals match local USD snapshots. The current Stripe API supports `allowed_payment_method_types: ["card"]`, a filter on dynamic payment methods. This enforces immediate cards and compatible card wallets without changing account resources or maintaining an exclusion list; Link and delayed methods are excluded in this initial lifecycle. Browser QA showed Link wallet bank choices despite the filter, so `wallet_options.link.display=never` explicitly hides Link as well. A Dashboard configuration is optional, not required. No automatic tax until tax treatment/registrations are approved. No shipping collection, accounts, subscriptions, discounts, marketing enrollment, custom email or SMS.

Use a minimum-supported approximately 30-minute Session lifetime. Persist the complete Session request for safe idempotent retry. Holds are released only after confirmed Stripe expiration, or after proving no Session creation can still succeed. A scheduled authenticated reconciler recovers interrupted creation and missed webhooks. Refunds change financial status but never automatically restock bakery inventory.

Guest name/email are collected by Checkout; phone is disabled initially. Success summaries require a browser capability cookie and omit contact details. Operator exports use local database credentials, never public endpoints. Commerce defaults off and the code rejects live keys. Live activation requires a separate explicit request and a reviewed launch gate.

Sources: [hosted Checkout](https://docs.stripe.com/payments/accept-a-payment?payment-ui=checkout&ui=stripe-hosted), [fulfillment](https://docs.stripe.com/checkout/fulfillment), [Session expiration](https://docs.stripe.com/api/checkout/sessions/expire), [idempotent requests](https://docs.stripe.com/api/idempotent_requests), [payment method configurations](https://docs.stripe.com/payments/payment-method-configurations).

The newsletter consent extension uses an optional, unchecked Salted cart-drawer checkbox before hosted Checkout. It retains a published CMS wording snapshot and explicit choice in Postgres, linked to the verified guest email through the existing order. Stripe's native promotional-consent checkbox remains disabled because its default state is jurisdiction-dependent. The hosted payment architecture is unchanged; no newsletter enrollment or delivery service is activated. See [marketing consent](marketing-consent.md).
